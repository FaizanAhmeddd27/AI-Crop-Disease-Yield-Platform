## 1. Executive Summary

AgriSense AI is a full-stack, AI-powered smart-agriculture web platform that helps farmers **(A) detect crop diseases early from a photo of a leaf** and **(B) estimate crop yield before harvest** from weather, soil, and historical data. Both results are shown together in a single dashboard.

The platform is built on two complementary AI pipelines:

1. **Computer Vision pipeline** — a fine-tuned deep-learning classifier (ResNet / EfficientNet / Vision Transformer) that returns *disease, confidence, severity*, plus a **Grad-CAM** heatmap showing *why*.
2. **ML / Time-Series pipeline** — a yield predictor (Linear Regression → Random Forest → XGBoost → LSTM/Transformer where data supports it) that returns *predicted yield, risk level, and top influencing factors*, explained with **SHAP**.

The product is deliberately **explainable**: users don't just get a label or a number; they see what drove it. Treatment advice is **not generated by the classifier**; it comes from a curated, trusted agricultural knowledge source.

The project doubles as an applied AI product **and** an academic/research project: it includes measurable experiments, experiment tracking (file-based run records), explainability, and a deployable cloud application.

## 2. Problem Statement

| Problem | Impact |
|---|---|
| Crop diseases are often identified late or incorrectly by eye. | Yield loss, over/under-use of chemicals, wasted money. |
| Farmers lack a pre-harvest view of expected production. | Poor planning for storage, labour, sales, and finances. |
| Existing AI tools are "black boxes" — they give an answer with no reasoning. | Low trust; farmers and agronomists can't verify the output. |
| Weather, soil, and history data exist but are fragmented. | Hard for a non-technical user to turn into decisions. |

**Opportunity:** combine disease detection and yield forecasting in one simple, explainable, web-accessible tool.

## 3. Vision, Objective & Goals

**Project Objective (from source brief):** Help farmers detect crop diseases early and make better production decisions by providing AI-driven crop-health insights and pre-harvest yield forecasts in one accessible platform.

### 3.1 Product Goals
| ID | Goal |
|---|---|
| G1 | Let a farmer upload a leaf photo and receive disease, confidence, and severity in seconds. |
| G2 | Visually explain every disease prediction (Grad-CAM). |
| G3 | Let a farmer enter crop/location/farm info and receive predicted yield, risk level, and key drivers. |
| G4 | Explain every yield prediction with feature-level attributions (SHAP). |
| G5 | Present crop-health and yield outlook together in one dashboard. |
| G6 | Provide disease-specific recommended actions from a trusted knowledge source (never invented by the model). |

### 3.2 Engineering / Academic Goals
| ID | Goal |
|---|---|
| E1 | Run a **comparative experimental workflow** (baseline CNN vs. pretrained CNNs vs. ViT; LR vs. RF vs. XGBoost vs. LSTM/Transformer). |
| E2 | Track every experiment, parameter, metric, and model version in a **durable run record** for reproducibility. |
| E3 | Evaluate generalization honestly (PlantVillage lab images **vs.** real-world/field images). |
| E4 | Deliver a **deployable** full-stack app (Docker, Vercel, Render/Hugging Face/Cloud). |
| E5 | Demonstrate skills across CV, DL, tabular ML, time-series, XAI, APIs, frontend, MLOps, and cloud. |

### 3.3 Non-Goals (for the initial semester version)
- Not a certified agronomic or pesticide-prescription system; outputs are decision support only.
- No real-time drone/satellite/IoT sensor ingestion.
- No native mobile app (the web app must be mobile-responsive instead).
- No payments, marketplace, or multi-tenant enterprise features.
- No free-text LLM treatment generation (RAG assistant is a *future* extension).
- No guarantee of accuracy on crops/diseases outside the supported list.

## 7. Feature Specifications

### F1 — Crop Disease Detection
**Input:** one leaf image (JPEG/PNG/WebP, ≤ 10 MB), crop type optional (helps filter/validate).
**Processing:** validate → resize/normalize → classifier (fine-tuned ResNet/EfficientNet/ViT, best model selected by experiments) → softmax → threshold check.
**Output:**
- Predicted class (crop + disease, or healthy)
- Confidence score (0–100%)
- Top-3 alternatives (Should)
- **Severity**: Healthy / Low / Moderate / Severe (see 7.3 for method and caveats)
- Grad-CAM overlay image
- Recommended actions (from knowledge base)
- "Uncertain" state when confidence below threshold, with guidance to retake photo

**Acceptance (summary):** see `SRS.md` FR-D-001 … FR-D-020.

### F2 — Crop Yield Prediction
**Input:** crop type, location (lat/lon or region pick), sowing/season info, area (optional), soil properties (auto/manual), weather window, historical yield (from dataset).
**Processing:** feature assembly → weather retrieval (Open-Meteo / NASA POWER) → preprocessing → yield model (best of LR / RF / XGBoost / LSTM / Transformer) → risk classification → SHAP.
**Output:**
- Predicted yield (units shown clearly, e.g., t/ha)
- Prediction range (Should)
- **Risk level**: Low / Medium / High
- Top contributing features (SHAP bar/waterfall in plain language)
- Comparison to historical average (Should)

### F3 — Explainability
| Pipeline | Method | User-facing form |
|---|---|---|
| Disease | **Grad-CAM** | Heatmap overlay on the uploaded leaf with caption ("Highlighted areas influenced the decision most"). |
| Yield | **SHAP** | Ranked feature-contribution chart + plain-language sentences ("Low rainfall in July reduced predicted yield"). |

### F4 — Recommended Actions (Knowledge Base)
- A **curated disease-knowledge table** (symptoms, cause, cultural/chemical/organic management, prevention, sources).
- Content comes from trusted agricultural sources (e.g., university extension services, FAO, national agriculture departments) — each entry stores its source reference.
- Always displayed with a disclaimer: *"Decision support only; confirm with a local agronomist before applying chemicals."*
- The classifier **never** produces treatment text.

### F5 — Results Dashboard
- Cards: *Latest Crop Health* (disease, severity, thumbnail+heatmap) and *Yield Outlook* (value, risk, top drivers).
- Charts (Recharts): yield vs. historical average, weather trend, SHAP bars, confidence bars.
- Link to detailed pages.

### F6 — Weather & Data Retrieval
- Open-Meteo (default, no key) and NASA POWER (historical/agro-climate) behind a single `weather_service` abstraction with fallback and caching.

### F7 — History & Accounts (Could / Stretch)
- Supabase Auth; saved predictions; list & detail views.

### F8 — Model Transparency Page (Should)
- Model Card: data used, metrics, class list, known limitations, version.

### F9 — MLOps Back-office (Developer-facing)
- Run tracking: experiments, params, metrics, artifacts and model versions recorded per run; reproducible configs; one promoted "production" version per pipeline.

### 7.3 Severity Estimation — Design Note (important)
The brief requires an "estimated severity level." The PlantVillage dataset has **no severity labels**, so severity cannot be learned directly. Planned approach (documented honestly as an *estimate*):
1. **Primary:** segment leaf area and lesion area (colour-space/threshold-based, optionally a lightweight segmentation model) → `severity_ratio = lesion_pixels / leaf_pixels` → map to bands (e.g., <10% Low, 10–30% Moderate, >30% Severe; bands tunable).
2. **Supporting signal:** Grad-CAM coverage area and classifier confidence.
3. **Healthy** predictions return severity = "None".
4. UI labels it **"Estimated severity"** with a tooltip explaining the method and its limits.
5. Validate on a small manually-annotated subset (e.g., 50–100 images) and report agreement.

## 11. Assumptions & Constraints

**Assumptions** (confirm/adjust — see §15):
1. Initial disease classes come from **PlantVillage** (38 classes across 14 crops; some distributions add a background class).
2. Yield modelling will focus on **a small set of crops (2–3)** in **one geography**, chosen by data availability.
3. Training happens on **Kaggle Notebooks (GPU)**; inference runs on **CPU** in production.
4. Team is small (1–3 people); semester timeline ≈ 14 weeks.
5. Free/low-cost tiers are used for hosting and storage during the semester.

**Constraints**
- Free-tier hosting limits (RAM, cold starts, request timeouts) shape model size and serving strategy.
- Kaggle sessions are ephemeral (no persistent disk) → checkpoints and experiment logs must be persisted to Supabase Storage or a versioned Kaggle Dataset.
- Public-dataset licensing/terms must be respected and cited.
- PlantVillage is lab-style imagery → expected performance drop on field images.

## 13. Risks & Mitigations
| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Model overfits PlantVillage; fails on real photos | High | High | Augmentation (background, lighting), small real-world eval set, honest reporting, confidence threshold + "uncertain" UX |
| R2 | Yield data is sparse/low-quality for chosen crop/region | Med | High | Choose crops by data availability first; start with tabular baselines; only use LSTM/Transformer if temporal data supports it |
| R3 | Severity has no ground truth | High | Med | Heuristic lesion-ratio method, labelled "estimated", validated on small annotated subset |
| R4 | Free-tier backend can't hold PyTorch models (RAM/cold start) | Med | High | Choose compact model (e.g., EfficientNet-B0/ResNet-50), ONNX Runtime, lazy-load, Hugging Face Spaces as alternative |
| R5 | Kaggle session killed at the weekly quota / 12 h limit loses all progress | High | Med | Checkpoint to Supabase Storage every epoch; push run records out each session; resumable training script with a time budget |
| R6 | Harmful/incorrect treatment advice | Low | High | Curated KB only, source citations, disclaimers, no model-generated advice |
| R7 | Scope creep (RAG, agents, alerts) | High | Med | Strict MVP scope; extensions documented but gated behind Phase 10 |
| R8 | External API changes/outages | Med | Med | Provider abstraction, caching, manual-entry fallback |
| R9 | SHAP/Grad-CAM misread as ground truth | Med | Med | UI copy explains they show *model attention/attribution*, not causation |
| R10 | Privacy of uploaded images/location | Med | Med | Minimal data retention, private bucket, signed URLs, clear privacy note, deletion option |
